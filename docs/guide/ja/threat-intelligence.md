# ライブ脅威情報

[English](../threat-intelligence.md) · **日本語**

ロックファイルのスキャナが答えるのは「依存しているパッケージに脆弱性があるか」です。しかし多くのインシデントは別の所から始まります。インタープリタやサーバーのリリース（PHP や OpenSSL の緊急パッチ）、インターネットに面した製品（BI ツール、アプリケーションサーバーの管理画面）、公開されるべきでなかったファイルなどです。そのためどの監査でも、どの深さでも、リポジトリが**デプロイしているもの**を監査の時点で取得した脆弱性情報と照合します。誰かがインシデントの名前を指定する必要はありません。

![ライブ脅威情報の流れ。リポジトリのバージョン指定を platform_inventory.py がネットワークなしで読み、各コンポーネントのバージョン、精度、文脈、露出のシグナルを platform.json に書く。threat_intel.py はバックグラウンドで海外のフィード（CISA KEV、NVD、FIRST EPSS、endoflife.date）と国内のフィード（IPA、JPCERT/CC、JVN、JVN iPedia）に照合し、送るのは製品名とバージョンだけ。取得に失敗したフィードは未確認範囲として明記し、合格扱いにしない。intel.json はコンポーネントを act-now、review、update に分類し、supply-chain-infra レーンが重大度の下限に従って判定し、報告書の第 2 章にバージョン、勧告 ID、フィードの日付と未取得分を載せる。](../../assets/threat-intel-flow.ja.svg)

## 手順 1：platform_inventory.py

`platform_inventory.py` はすべてのリポジトリで、ネットワークを使わず数秒で動きます。ロックファイルのスキャナが見ない場所からバージョンを見つけます。

- Dockerfile の `FROM` と `ARG` の既定値（マルチステージビルドを含む）
- compose ファイル、Kubernetes のマニフェスト、Helm チャート
- `.tool-versions` や `.nvmrc` などのバージョンファイル
- CI のセットアップ手順とサーバーレスのランタイム
- ロックファイル内のフレームワークの項目

コンポーネントごとに、バージョン、指定箇所の `path:line`、そして照合結果の意味を決める 2 つの属性を記録します。

| 属性 | 値 | 意味 |
|---|---|---|
| 精度 | `exact`（x.y.z）、`minor`、`major`、`floating`（`php:8.3-fpm`、`node:20`、`latest`）、`range`（`^8.1`、`>=18`）、`distro`（apt や apk のパッケージ）、`managed`（Lambda、App Engine、Functions） | exact の指定は根拠になります。floating のタグは最後にビルドしたときのものです。distro のパッケージは修正がバックポートされている場合があるため、実行環境での確認が必要です。managed のランタイムは提供者が修正するため、問題になるのはサポート期間だけです。range は許される最も古い系列で判断します。 |
| 文脈 | `deploy`、`build`、`ci`、`dev`、`declared` | `deploy`（最終イメージのステージ、compose、マニフェスト、サーバーレス）が実際に動くものです。それ以外は意図を示すだけで、本番を示すものではありません。 |

露出と堅牢化のシグナル（結論ではなく手がかり）も記録します。Web ルート下の `.env` やダンプ、`phpinfo()`、ディレクトリ一覧の表示、管理ツールや BI ツールのイメージ、公開されたデータストアのポート、Spring Actuator の露出、Tomcat の manager ロール、root で動くコンテナ、ランタイムイメージ内のダウンロードツール、リモートの `ADD`、ダイジェストのないベースイメージ、Kubernetes の NetworkPolicy がないこと、宛先を制限しないセキュリティグループの外向き通信、ベースイメージの自動更新がないこと、などです。

出力：`work/<repo>/platform.md` と `platform.json`。

## 手順 2：threat_intel.py

すべてのリポジトリに対して 1 つのバックグラウンドのコマンドが、一覧を <!--n:feeds-->8<!--/n--> つのフィードと照合します。所要時間は 10-90 秒で、NVD の API キーがなければもっと長くかかります。

| フィード | 範囲 | 答えること | 注意点 |
|---|---|---|---|
| CISA KEV カタログ（予備に GitHub のミラー） | 海外 | 実際に悪用されているか、ランサムウェアでの使用 | 米国中心の選定 |
| NVD CVE API 2.0 | 海外 | このバージョンに該当する CVE（CPE + バージョン） | CPE のデータは新しい CVE から数日から数週間遅れることがあり、キーなしではレート制限があります |
| FIRST EPSS | 海外 | 30 日以内に悪用される確率 | 毎日更新 |
| endoflife.date | 海外 | サポート期間とセキュリティ期間、系列ごとの最新パッチ | コミュニティが管理しています。P0 や P1 の判断にはベンダーのページも確認します |
| IPA 重要なセキュリティ情報 | 国内 | 国の機関が求める緊急の対策 | 件数は少なく、重要度は高い |
| JPCERT/CC 注意喚起 | 国内 | 注意喚起、週報、痕跡情報付きの攻撃キャンペーンの注意喚起 | |
| JVN | 国内 | 調整済みのベンダーアドバイザリ（JVN#、JVNVU#）、国内製品 | |
| JVN iPedia | 国内 | より広い脆弱性データベース | 停止することがあります。JVN と JPCERT/CC で補います |

出力は、レーン向けの `work/intel.md` と、報告書と検証スクリプト向けの `work/intel.json` です。各コンポーネントには優先度が付きます。

| 優先度 | 意味 |
|---|---|
| `act-now` | 指定されたバージョンに、KEV の CVE、または国内の注意喚起で今すぐの修正を求められている CVE がある |
| `review` | サポート終了、バージョンの一致を確認できない注意喚起、深刻な CVE |
| `update` | 系列の最新パッチより古い |

### 重大度の下限

| 状況 | 重大度の下限 |
|---|---|
| デプロイしている exact のバージョンが KEV または国内で注意喚起された CVE の影響を受け、インターネットから到達できる | 認証前の RCE や認証回避なら P0、それ以外は P1 |
| 同上で、インターネットから到達できない（内部のデータストア、CI のイメージ） | P1 |
| 系列の最新パッチより古く、CVSS 9 以上または EPSS 0.1 以上の CVE がある | P1 |
| ランタイム、OS、データストア、フレームワークの系列が deploy の文脈でサポート終了 | インターネットに面していれば P1、それ以外は P2 |
| 管理ツール、BI ツール、管理画面、データストアに外部から認証なしで到達できる | データを持つかコード実行ができれば P0、それ以外は P1 |
| 秘密情報を含むファイルが公開される Web ルートの下にコミットされている | 秘密情報や個人データを含めば P0、それ以外は P1 |

是正策ごとに 1 件にまとめます。「Dockerfile で PHP を修正済みのバージョンに上げ、再ビルドして再デプロイする」という 1 件に、それで解消するすべての CVE と、変更が必要なすべての指定箇所を列挙します。是正策には最小の修正済みバージョンと、アドバイザリが示す暫定的な緩和策を書きます。Dockerfile を直しても、再ビルドと再デプロイをするまでサーバーは直っていないからです。

規則の詳細：[`threat-intel.md`](https://github.com/nguyenhx2/agent-security-audit/blob/main/editions/ja/security-audit/reference/method/threat-intel.md)。

## ネットワークに送るもの

| 送るもの | 送信先 |
|---|---|
| endoflife.date の製品 ID | endoflife.date |
| `cpe:2.3:a:php:php:8.3.30` のような NVD の CPE 文字列 | NVD |
| CVE 番号 | FIRST EPSS |
| なし（取得のみ） | CISA KEV、IPA、JPCERT/CC、JVN、JVN iPedia |

リポジトリ名、パス、コード、指摘内容は送りません。接続するのは固定の許可リストにあるホストだけで、それ以外のホストへのリダイレクトは拒否します。フィードの文章は信頼しないデータとして扱います。タイトルから制御文字、双方向制御文字、ゼロ幅文字を取り除いて切り詰め、リンクはそのフィード自身のホストのものだけを残し、フィードの内容に従うことも実行することもありません。

## 失敗したフィードは未確認範囲として明記する

どのフィードも必須ではありません。タイムアウトしたり、エラーページを返したり、停止していたりするフィードは、`intel.md` と報告書の第 2 章に未確認範囲として記載し、黙って合格扱いにすることはありません。`threat_intel.py` はフィードが失敗しても終了コード 0 で終わるため、監査は続きます。脆弱性情報は毎日変わるため、報告書にはフィードの日付を記載し、その日付時点の内容であることを示します。

`intel.json` にある悪用が確認された CVE や国内で注意喚起された CVE、サポート終了の deploy コンポーネントが、どの指摘事項にも含まれず、理由付きの反証にも載っていない場合、検証スクリプトが警告します。

## キャッシュとオフラインでの利用

| オプション | 効果 |
|---|---|
| 既定 | 応答はフィードごとの有効期間付きで `~/.cache/security-audit/intel` にキャッシュします。フィードが落ちているときは、キャッシュを古いものとして明記したうえで使います。 |
| `--offline` | キャッシュのみを使い、ネットワークは使いません。ないフィードは未確認範囲になります。ネットワークの利用が認められないときに選び、スキルは報告書にその旨を明記します。 |
| `--cache-dir DIR` | 別のキャッシュフォルダを使います。 |
| `NVD_API_KEY`（環境変数） | NVD のレート制限を緩めます。それ以外にアカウントは必要ありません。 |
| `--no-nvd`、`--max-nvd N` | バージョンごとの NVD への問い合わせを省略、または上限を設けます（キーがないと遅いため）。 |
| `--days N` | 国内の注意喚起と KEV の新規項目を見る期間（既定は 60 日）。 |

ネットワークを一切使わずに監査したいときは、開始時にそう伝えてください（「ネットワークは使わないで」）。脆弱性情報の照合は `--offline` で実行します。

## 「この注意喚起の影響を受けるか」

1 つのアドバイザリについての質問にも、同じ仕組みで答えます。たとえば次のように頼みます。

```text
CVE-2026-XXXXX の影響を受けるか確認して
/security-audit ../shop-api quick
注意喚起の影響確認
```

通常は Quick で十分です。プラットフォーム一覧が、各リポジトリがその製品のどのバージョンをデプロイし、どこで指定しているかを示し、照合結果が、そのバージョンが KEV、NVD、国内の注意喚起に載っているかを示します。国内の注意喚起が製品名を挙げていても NVD の CPE データでバージョンを確認できない場合（`named in alerts, version match unconfirmed`）、レーンがアドバイザリの影響を受けるバージョンの一覧を読み、指定と比べます。その比較が根拠になります。`declared` や floating の指定しかない場合、指摘事項にはデプロイ中のバージョンが不明であることと、それを判断するために実行環境で確認すべきことを書きます。

## 限界

- **静的な分析である。** デプロイされたバージョンはリポジトリと違うことがあります（その場で修正されたホスト、PaaS のイメージ、同じタグの新しいビルド）。指摘事項には、どの指定に基づくかを書きます。
- **フィードは選ばれた情報である。** NVD の CPE 照合は、名前の付け方が違う製品やまだ分析されていない CVE を見逃します。KEV は選定された一覧で、国内の注意喚起は各機関が公表したものだけです。非公開のフォークや一覧にないベンダー製品は、照合できなかったものとして記録します。
