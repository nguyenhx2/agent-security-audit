# 初めての監査

[English](../first-audit.md) · **日本語**

## 始め方

普通の言葉で頼むか、スキルの名前で呼び出します。次のどれでも監査が始まります。

```text
このリポジトリをセキュリティ監査して
セキュリティ監査
脆弱性診断
注意喚起の影響確認
audit this repo
security review before launch
check for leaked credentials
are we affected by this CVE
```

明示的に呼び出す形では、パス、深さ、2 つのスイッチを指定できます。

```text
/security-audit [repo-path ...] [quick|standard|deep] [--yes] [--keep-work|--purge-work]
```

| 引数 | 効果 |
|---|---|
| `repo-path ...` | 監査するリポジトリ（1 つ以上）。省略すると現在のリポジトリです。複数指定すると、1 回の監査で 1 つの報告書になります。 |
| `quick`、`standard`、`deep` | 深さ。ここで指定すると、深さの質問は省略されます。 |
| `--yes` | すべての質問を省略し、既定値を使います（下記）。無人で実行するときに使います。 |
| `--keep-work` / `--purge-work` | 最後に中間ファイルの `work/` フォルダをどうするか（[指摘事項と報告書](reports.md)を参照）。 |

例：

```text
/security-audit ../shop-api deep
/security-audit ../shop-api ../shop-web standard
/security-audit C:/src/shop-api quick --yes
```

**中立なフォルダから始めてください。** 監査するリポジトリが現在の作業フォルダで、`.claude/`、`.mcp.json`、`CLAUDE.md` のいずれかを含む場合、そのフック、MCP サーバー、指示は Claude Code のセッションで有効になっています。スキルはそのことを伝え、リポジトリの外のフォルダ（たとえば親フォルダ）から監査を始めるよう勧めます。

## Phase 0 の質問

スキルはまずリポジトリの特徴を調べ（`detect_stack.py`）、そのあと最大 5 つの質問を 1 回か 2 回に分けて、依頼に使われた言語で尋ねます。依頼の中ですでに答えている質問は省きます。

| 質問 | 選択肢 | 質問しないときの既定値 |
|---|---|---|
| **深さ** | 詳細（Deep、推奨）、標準（Standard）、クイック（Quick）。質問にはリポジトリの規模も表示されます。 | 引数、なければ Deep |
| **報告書の言語**（複数可） | 日本語、English、または「Other」（任意の言語） | 依頼に使われた言語 |
| **重点**（複数可） | アプリケーションセキュリティ、シークレットとサプライチェーン、機微データ、性能と品質。AI の範囲やモバイルアプリを検出した場合は、専用の選択肢が加わります。コードに現れない業種は「Other」で追加できます。 | 検出したすべてのレーン |
| **形式**（複数可） | HTML、Excel。Markdown は常に作成します。質問には出力先のフォルダも表示され、「Other」で変更できます。 | Markdown、HTML、Excel |
| **法令**（個人、決済、健康、金融のデータを検出したときのみ） | GDPR（EU/英国）、個人情報保護法（APPI）、ベトナム PDPL、米国（CCPA・HIPAA） | なし。プライバシー上の義務は一般的な形で引用し、そのことを明記します |

選ばなかった重点領域は、黙って外すのではなく未確認範囲として列挙します。利用者が申告した業種（「うちは銀行です」「市役所向けのシステムです」）は、コードに現れていなくても加えます。

これらに答えたあと（または `--yes` で省略したあと）は、もう一度質問のために止まることなく、報告書まで実行します。そのためヘッドレスの実行（`claude -p`）でも、必ず指摘事項と報告書が残ります。

## 深さ

| 深さ | 実行する内容 | 主な用途 |
|---|---|---|
| **Quick** | すべてのスクリプトとスキャナを実行し、そのあと最大 3 つのレビューレーン（`authz-logic`、リポジトリの種類に応じた主要レーン、`injection-dataflow`）をメインセッション内で実行します。P0 と P1 はリードが自分で再確認します。サブエージェントは使いません。 | 最初の確認、小さなリポジトリ、「この CVE の影響を受けるか」 |
| **Standard** | すべてのスクリプトとスキャナ、`recon-mapper`（Sonnet、medium）、並列の lane-reviewer グループ（Sonnet。設計系レーンは high、その他は medium）、P0 と P1 の `finding-verifier`（Sonnet、high）。 | 定期的な監査 |
| **Deep**（既定） | Standard と同じ構成で、設計系レーン（`authz-logic`、`sensitive-data`、`ai-agentic`）を Opus（high）、その他のレーンを Sonnet（high）で実行し、検証役は Opus（high）で P0 から P2 までを対象にします。網羅性チェックリストのすべての行を確認します。 | リリース前、規制のあるシステム |

どの深さでも、プラットフォーム一覧、ライブ脅威情報、機微データのスイープ、スキャナは実行します。変わるのは、レビューレーンの数、コードを読むモデル、反証による検証の範囲です。`perf-quality` は Standard と Deep だけで実行し、Quick では未確認範囲として明記します。詳しくは[モデルと費用](models.md)を参照してください。

### 費用と時間

| 深さ | 実測値 |
|---|---|
| Quick | ライブのベンチマークでは、意図的に脆弱にした 3 つのプロジェクトに対し、監査 1 回あたり平均 US$<!--n:bench_cost_usd-->2.52<!--/n-->、<!--n:bench_minutes-->8<!--/n--> 分でした（[benchmark/RESULTS.ja.md](https://github.com/nguyenhx2/agent-security-audit/blob/main/benchmark/RESULTS.ja.md)）。深さの質問では、Quick は約 5-10 分と説明しています。 |
| Standard、Deep | ベンチマークは取っていません。サブエージェントが増え、より強いモデルを使うため、Quick より時間も費用もかかると考えてください。 |

監査の中では、スキャナはイメージがキャッシュにあればリポジトリごとに約 1-5 分（最初のイメージ取得でさらに 1-5 分）、脆弱性情報との照合は 10-90 秒（`NVD_API_KEY` がなければもっと長く）かかります。どちらもバックグラウンドで動き、その間に偵察とスイープが進みます。

## 報告書の言語と形式

- **日本語と英語**は、見出し、ラベル、本文、HTML と Excel の画面まで完全に対応しています。
- **それ以外の言語**（「Other」）は、本文がその言語、ラベルが英語になります。
- **複数の言語**を選ぶと、言語ごとに指摘事項と報告書の一式を作ります。2 つ目の言語は指摘事項データの翻訳で、監査をやり直すわけではありません。そのため ID、重大度、アンカーはどの言語でも同じです。
- **会話の言語**（質問、進捗、最後の返答）は依頼に使われた言語に従い、報告書の言語とは別に決まります。

| 形式 | 常に作成？ | 内容 |
|---|---|---|
| Markdown | はい | 検証済みの正本 |
| HTML | 選んだとき | 検索、絞り込み、並べ替え、指摘事項の展開ができる、オフラインで開ける 1 ファイル |
| Excel | 選んだとき | グラフ、ドロップダウン、担当者・期限・メモの列を持つ進捗管理用のブック。`openpyxl` が必要です。 |

詳しくは[指摘事項と報告書](reports.md)を参照してください。

## 出力の場所

出力はすべて、リポジトリの**隣**の日時付きフォルダに置き、リポジトリの中には書きません。

```text
<parent-of-repo>/<project>-security-audit/<YYYY-MM-DD_HHMM>/
  reports/md/    security-audit-report_<project>_<ts>[_<lang>].md   常に作成、検証済み
  reports/html/  ..._<ts>[_<lang>].html                             選択したとき
  reports/xlsx/  ..._<ts>[_<lang>].xlsx                             選択したとき
  findings/<lang>/<repo>/find-<repo>-001.md                         根本原因ごとに 1 ファイル
  work/                                                             中間ファイル、最後に整理
```

`<project>` は、利用者が指定した製品名、なければリポジトリ名、複数のリポジトリならその名前を `-` でつないだものです。ファイル名は小文字です。再実行しても上書きはしません。新しい日時で新しいフォルダを作ります（同じ分に 2 回実行すると `_2` が付きます）。`_<lang>` は、報告書の言語を 2 つ以上選んだときだけ付きます。複数のリポジトリを監査する場合、フォルダはそれらの共通の親フォルダに置きます。

形式の質問で、別の出力先を指定することもできます。

## 実例

`C:/src/shop-api` にある Node.js の API を、リリース前に定期監査したいとします。報告書はチーム向けに英語、パートナー向けに日本語で必要です。

1. リポジトリではなく親フォルダの `C:/src` で Claude Code を開き、次のように入力します。

   ```text
   /security-audit shop-api standard
   ```

2. スキルが `env_check.py` と `detect_stack.py` を実行し、残りの質問をします。言語は **English** と **日本語** を選び、重点はすべてのまま、HTML と Excel もそのままにします。この API は顧客のアカウントを保存しているため法令も尋ねられ、**個人情報保護法（APPI）** を選びます。
3. スキャナがバックグラウンドで動き始め、続いてプラットフォーム一覧とライブの脆弱性情報の照合が始まります。それらが終わるまでの間に、偵察、機微データのスイープ、レビューレーンが進みます。
4. 検証役が P0 と P1 の候補それぞれの反証を試みます。残ったものが指摘事項ファイルになり、報告書を組み立て、検証し、描画します。翻訳のサブエージェントが、同じデータから日本語の一式を作ります。
5. 最後の返答は短く、P0 と P1 の件数、上位 3-5 件の指摘（`file:line` 付き）、最初に取るべき対応、未確認範囲、報告書のパスを示します。たとえば次のようなパスです。

   ```text
   C:/src/shop-api-security-audit/2026-10-30_1015/reports/html/security-audit-report_shop-api_2026-10-30_1015_en.html
   C:/src/shop-api-security-audit/2026-10-30_1015/reports/html/security-audit-report_shop-api_2026-10-30_1015_ja.html
   ```

HTML の報告書を開いて重大度で並べ替え、Excel のブックで担当者を割り当て、修正します。修正が終わったら「修正を確認するために再スキャンして」と頼みます（[再スキャンと修正の確認](rescan.md)）。

実際の結果は、README に、練習用に意図的に脆弱にしたアプリ DVWA を Quick で監査した画面例（指摘 19 件）があります（[README：報告書の見た目](https://github.com/nguyenhx2/agent-security-audit/blob/main/README.ja.md#報告書の見た目)）。
