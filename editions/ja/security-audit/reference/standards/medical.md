# モジュール：medical - 健康情報と患者データ（日本の医療情報ガイドライン、HIPAA への参照）

システムが患者、診療、健診、問診票、症状、服薬その他の健康データを保存または処理する場合に適用する
（detect のフラグ `health`）。健康データは Japan APPI の要配慮個人情報であり、GDPR / Vietnam PDPL の
機微な個人データである。このモジュールは `reference/standards/privacy.md` に業種別の規則を上乗せする。
バージョンは `reference/standards/index.md` に従う。

## 1. ガイドラインの体系（3省2ガイドライン）
日本は医療情報システムを、互いに補完する 2 つのガイドライン（合わせて 3省2ガイドライン と呼ぶ）で
規律している：

| 正規名（これを引用する） | 正式名称 | 発行者 | 版 | 対象 |
|---|---|---|---|---|
| `MHLW Medical Information Security Guidelines` | 医療情報システムの安全管理に関するガイドライン | 厚生労働省 | **第7.0版** | 医療機関等と、それが利用するシステム。5 編構成：概説編、経営管理編、企画管理編、システム運用編、保守委託機関編（第7.0版で新設） |
| `MIC/METI Medical Service Provider Guidelines` | 医療情報を取り扱う情報システム・サービスの提供事業者における安全管理ガイドライン | 総務省 + 経済産業省 | **第2.0版** | 医療機関等のために医療情報を扱うシステムを構築または運用する事業者：SaaS、クラウド、API 提供者、受託開発事業者 |

クリニック向けに患者アプリや API を構築する事業者は総務省・経産省のガイドラインに直接拘束され、
医療機関が厚労省のガイドラインを満たせるようにしなければならない。そのため指摘事項は通常両方を引用する。
どちらのガイドラインもコードと一対一には対応しない：義務の根拠としてガイドラインを引用し、それぞれに
検証可能な管理策（`OWASP ASVS 5.0.0`、`OWASP API Security Top 10 2023`、`Japan APPI`）を組み合わせる。

## 2. コードから根拠を示せる確認項目
| ID | 要件 | コードで検証する内容 | 場所 / grep のヒント | 検出 |
|---|---|---|---|---|
| M01 | 医療機関間の分離（マルチテナント） | 患者または施設が所有する行へのクエリはすべて、呼び出し元に認可された施設 / テナントで絞り込む。連番や推測可能な ID で施設をまたいでレコードに到達できない。患者と施設の連携には ID だけでなく第 2 の要素（施設側の承認、ワンタイムの連携コード）が必要 | 施設 / テナント ID のカラム、結合、リポジトリのメソッド、連携 / 招待のエンドポイント、`routes.md` | M |
| M02 | 患者データは本人にのみ（BOLA） | 患者 ID は検証済みのセッションまたはトークンから取得し、パス、クエリ、ボディのパラメータからは決して取得しない。日記、問診票、結果の更新と削除で所有者を確認する | `get_current_patient` のような依存関係、`patient_id` という名前のパスパラメータ、管理者用と患者用のルート | M |
| M03 | 真正性・見読性・保存性 | 診療記録を誰がいつ作成し変更したかが記録され、クライアントから書き換えられない。論理削除で履歴が残る。スコアや結果はサーバー側で計算し、クライアントから受け取らない | `created_by`、`updated_at`、論理削除フラグ、履歴 / 監査テーブル、スコア計算 | M |
| M04 | 通信時と保存時の暗号化 | 健康データを運ぶすべての経路で TLS。データベース、オブジェクトストレージ、バックアップのストレージ暗号化。脅威モデルが必要とする箇所ではフィールド単位の暗号化またはトークン化。コード内に鍵がない | DB / バケットの IaC、ORM の暗号化型、KMS の設定、接続文字列 | S+M |
| M05 | ログ、エラー、分析に健康データを出さない | ログ、例外メッセージ、SQL ログ、APM のトレース、分析イベントに氏名、生年月日、メッセージアプリのユーザー ID、問診の回答、日記の本文を決して含めない。エラー応答が内部情報を露出しない | リクエストボディやモデルを渡すロガー呼び出し、例外ハンドラ、SQL の echo 設定、分析の `track(` ペイロード | S+M |
| M06 | 外部システムとの整合性 | 外部の医療システムへの通知や呼び出しはデータベースのコミット後に（またはアウトボックス経由で）行い、二重送信や書きかけの状態を生まないタイムアウトとリトライを備える | トランザクション境界、`commit()` の順序、HTTP クライアントのタイムアウト、Webhook の送信側 | M |
| M07 | アクセスの監査証跡 | 誰が、いつ、どこから、どの患者の記録を閲覧、変更、エクスポートしたかを記録し保護する。職員や運用者による一括読み出しやエクスポートを検知できる | アクセスログのミドルウェア、監査テーブル、エクスポートのハンドラ、ログの保持（`reference/method/threat-intel.md` の検知の確認） | M |

引用するガイドラインの項番（2026-10-26 に公開本文と照合済み。「-」は単一の項番がないため、編と
トピックのみを引用する）：

|---|---|---|
| M01 | 14.2 アクセス権限の管理 | 5.1.5 リスク対応の設計、別紙2 の対策項目 |
| M02 | 14.1.1 利用者の識別・認証、14.2 | 5.1.5、別紙2 |
| M03 | -（真正性・見読性・保存性の要求事項） | 別紙2 |
| M04 | 13.3 暗号化、13.1-13.2 ネットワーク、7.2 外部からのアクセス | 別紙2 |
| M05 | - | 別紙2 |
| M06 | - | 5.1.4 リスク対応の選択 |
| M07 | 17.1 証跡のレビュー | 別紙2 |
| バックアップ | 12.2 バックアップ | 別紙2 |

ガイドラインが重視する運用側も確認する：最小権限の管理者ロール、リモートアクセスと管理アクセスへの
MFA、記録され時間が限定された保守事業者のアクセス経路（保守委託機関編）、ランサムウェアが到達できない
バックアップ、文書化されたインシデント連絡先。

## 3. 重大度
- **P0：** 未認証の利用者、または任意の患者が、他の患者や他の施設の医療データを読み取りまたは変更できる
  （M01 / M02）。健康データが公開到達可能なストアにある。
- **P1：** 認証の背後で患者の絞り込みがクライアント指定の ID に依存している。健康データが日常的にログや
  第三者の分析サービスに書き込まれる。ID だけで施設と連携できる。診療記録のアクセス監査証跡がない。
- **P2：** 外部の医療システム呼び出しでタイムアウトやコミット順序が欠けている。論理削除や履歴の扱いが
  一貫していない。設定ミスで本番環境でも有効になりうる開発用の認証バイパスがある。

## 4. 引用の形式
上表の項番を引用する。それ以外は編 + トピックを引用する。項番は版の間で変わったため、第6.0版の項番を
第7.0版に流用してはならない。

```
standard: MHLW Medical Information Security Guidelines
standard_version: 7.0
requirement_id: システム運用編 14.2
also_maps_to: "MIC/METI Medical Service Provider Guidelines 2.0; OWASP API Security Top 10 2023 API1; Japan APPI Art. 23"
```
ここで使う APPI の条文：第20条第2項 要配慮個人情報の取得に関する同意、第23条 安全管理措置、
第26条 個人情報保護委員会と本人への漏えい等の報告（`reference/standards/privacy.md`）。

## 5. 日本以外
- 米国：covered entities および business associates には HIPAA Security Rule（45 CFR 164.312 技術的保護措置）-
  `reference/standards/privacy.md`。
- EU / 英国：GDPR Art. 9 特別な種類のデータ + Art. 32 処理のセキュリティ。
- ベトナム：PDPL の機微な個人データ（健康）。
M01-M07 の確認項目はどこでも適用される。変わるのは引用だけである。
