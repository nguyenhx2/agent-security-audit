# モジュール：pci-dss - コード監査で根拠を示せる PCI DSS v4.0.1 の要件

システムがカード会員データ（CHD）を扱う場合、またはそのセキュリティに影響し得る場合（決済ページ、
決済 SDK の組み込み、カード情報らしきカラム）に適用する。`PCI DSS v4.0.1 Req X.Y.Z` を引用する。将来日付の
要件はすべて 2025-03-31 時点で発効している（それまではベストプラクティス）。
保存に関する手順は `reference/method/sensitive-data-at-rest.md` にある - 最初にそれを実行する。

## 目次
- スコープの縮小 - 最初に判定すること
- コード / 設定 / IaC から根拠を示せる要件
- トランザクション整合性（資金移動）
- 静的監査では根拠を示せないもの

## スコープの縮小 - 最初に判定する
1. **カードデータは自社サーバーに触れるか？** Hosted fields / リダイレクト / iframe（Stripe Elements、Adyen
   Drop-in、PAY.JP checkout）は PAN をサーバーに通さない -> スコープは大幅に縮小。サーバー側での PAN 処理
   （API リクエスト内の生のカードフィールド）-> フルスコープ。リクエスト DTO とフォームをカードフィールドで grep する。
2. **事業者は何を返し、自社は何を永続化するか？** トークン/`last4`/ブランド/有効期限は問題ない。
   PAN、CVV、トラックデータは不可（sensitive-data-at-rest を参照）。
3. **決済ページ：** どのページが決済フォーム/iframe を読み込むか？ iframe が事業者のものであっても、
   それらのページは 6.4.3 および 11.6.1 のスコープに入る。

## コード / 設定 / IaC から根拠を示せる要件

| Req | 要件（要約） | ソースで検証する内容 | 重大度の下限 |
|-----|----------------------|--------------------------|----------------|
| 3.2.1 | 保存するアカウントデータを最小限に保つ。保持期間 + 安全な削除を定義 | 決済テーブルの保持ジョブ / TTL。パージ経路 | なければ P2 |
| **3.3.1**（3.3.1.1 track、3.3.1.2 CVV/CVC、3.3.1.3 PIN/PIN block） | **SAD はオーソリ後に保持しない（暗号化していても不可）** - データ要素に対応するサブ要件を引用する | CVV/track/PIN を保持するカラム、JSON blob、ログ、キャッシュ、キュー、分析データ | **P0** |
| 3.3.2 / 3.3.3 | オーソリ完了前に保存する SAD は暗号化。発行者の例外は限定的 | オーソリ前のキュー/キャッシュ | P1 |
| **3.4.1** | 表示時に PAN をマスク（最大で BIN + 下 4 桁）。ただし文書化された役割がそれ以上を必要とする場合を除く | 管理画面、領収書、メール、エクスポート、API 応答 | P1 |
| 3.4.2 | リモートアクセス時の PAN のコピー/移動を、許可された場合を除き防止 | エクスポート/ダウンロード機能 | P2 |
| **3.5.1** | **PAN は保存場所を問わず判読不能にする**（鍵管理を伴う強力な暗号、トランケーション、インデックストークン、鍵付きハッシュ） | 平文 PAN のカラム、ファイル、ログ、バックアップ。鍵なしハッシュは脆弱（総当たり可能） | 平文なら **P0** |
| 3.5.1.1 | PAN のハッシュは PAN 全体に対する鍵付き暗号学的ハッシュ（HMAC）でなければならない | 鍵なしの `sha256(pan)` -> 指摘事項 | P1 |
| 3.6 / 3.7 | 鍵管理：鍵の保護、最小限のアクセス、ローテーション、手動の場合は知識分割 | ハードコードされた鍵、データと同じ場所の鍵、ローテーション経路なし、KMS の利用状況 | P1 |
| 4.2.1 | オープン/公衆ネットワーク上の PAN に強力な暗号。証明書が有効 | `verify=False`、決済呼び出しの HTTP エンドポイント、TLS < 1.2 | P1 |
| 6.2.4 | ソフトウェアエンジニアリング手法により一般的な攻撃（インジェクション、XSS、アクセス制御など）を防止 | スコープ内コードの owasp-web 指摘事項に対応付け | 指摘事項に準じる |
| 6.3.2 | 独自開発およびサードパーティのソフトウェアコンポーネントの一覧（SBOM 相当） | ロックファイル + CI での SBOM 生成 | P2 |
| 6.3.3 | **Critical** なセキュリティパッチはリリースから 1 か月以内に適用。その他はリスクに基づく期間内 | 決済コンポーネントの依存関係の指摘事項 | 指摘事項に準じる |
| 6.4.1 / 6.4.2 | 公開 Web アプリを攻撃から保護（6.4.2：攻撃を検知・防止する自動化された技術的ソリューション、例：WAF） | 決済アプリの前段にある IaC またはエッジ設定の WAF / ボット対策設定 | 公開決済アプリで欠如していれば P2 |
| **6.4.3** | 決済ページのスクリプト：承認済み、完全性を保証（SRI/CSP ハッシュ）、正当化理由とともに一覧化 | SRI のないチェックアウトページ上の `<script src>`。決済ページ上のタグマネージャー。CSP の欠如 | P1 |
| 8.2.x / 8.3.x | 一意の ID、共有/汎用アカウントなし。CDE アクセスに MFA。強力な認証 | 管理者認証、サービスアカウント、設定内の共有認証情報 | P1 |
| 8.4.2 | CDE へのすべてのアクセスに MFA（リモート/管理者だけではない） | カードデータに到達する管理コンソールおよびバックオフィスアプリ。SSO/MFA の強制 | P1 |
| 8.3.6 | パスワードは 12 文字以上、数字 + 英字を含む（パスワードを使用する場合） | パスワードバリデータ | P2 |
| 8.6.2 | **対話型ログインに使用できる**アプリケーションおよびシステムアカウントのパスワード/パスフレーズをスクリプト/設定/ソースにハードコードしない（API キー / トークンには代わりに ASVS 5.0.0 V13 + CWE-798 を引用） | 決済関連シークレットの Gitleaks ヒット | 有効な事業者シークレットなら P0 |
| 10.2.x | 監査ログが CHD へのアクセス、管理操作、認証イベント、ログ変更を記録 | 決済操作周辺のロギング | P2 |
| 10.3.x | 監査ログを改ざんから保護 | ログシンク、追記専用テーブル | P2 |
| **11.6.1** | 決済ページの HTTP ヘッダーとスクリプト内容の変更/改ざん検知（毎週または TRA に基づく頻度） | CSP レポート、スクリプト完全性の監視、または事業者がホストするページ | P2（スクリプトが自社製かつ未監視なら P1） |
| 12.3.3 | 暗号スイート/プロトコルを一覧化しレビュー | IaC 内の TLS/暗号設定 | Info |

## トランザクション整合性（資金移動 - 単一の PCI 要件はない。性質を明記する）
返金、支払い、ウォレット、元帳が存在する場合は、その性質 + ASVS 5.0.0 V2（ビジネスロジック）/ V15（並行性）を引用する：
- **原子性：** 残高変更 + 元帳エントリ + 事業者呼び出しの結果を 1 つのトランザクション、または補償処理を伴う
  saga で扱う。ロールバックなしで複数の呼び出しに分割された書き込みを探す。
- **冪等性：** 外部から起動されるすべての資金操作（Webhook、リトライ、ダブルクリック）が、一意制約で強制される
  冪等性キーを持つ。重複排除のない Webhook ハンドラを探す。
- **競合状態：** 行ロック / 楽観的バージョニング（`SELECT ... FOR UPDATE`、バージョンカラム）のない
  残高の read-modify-write。同時リクエストによる二重支払いは P0/P1。
- **不変の監査証跡：** 追記専用の元帳。元帳の行に対する `UPDATE`/`DELETE` がない。
- **Webhook の真正性：** 事業者の署名を生のボディで検証、タイムスタンプの許容幅、
  リプレイ保護。検証処理の本体を読むこと - 何もしない検証処理は機能していないコントロールである（下限 P1）。

## 静的監査では根拠を示せないもの（Method-and-limitations に明記する）
ネットワークセグメンテーション（Req 1）、物理セキュリティ（9）、ASV スキャンとペネトレーションテスト（11.3/11.4）、ポリシー
と教育（12）、実際の鍵セレモニー。コード監査は QSA による評価を補完するものであり、決して代替しない。
