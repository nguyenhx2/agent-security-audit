# 指摘事項のトリアージ：重大度、確度、重複排除、検証、根拠付け

手順に戻る：`SKILL.md` の Phase 5-6。指摘事項の形式：`templates/finding.md.template`。

## 目次
- 結果に基づく重大度
- 引き下げ不可の強制ルール
- 確度（重大度とは別の軸）
- 敵対的検証（誤検知フィルタ）
- 根本原因による重複排除
- 根拠付け

## 結果に基づく重大度

| 重大度 | 定義（悪用された場合の結果による） |
|----------|------------------------------------------|
| **P0 / Blocker** | 現時点で到達可能な、直接的かつ影響の大きい侵害：カード会員データ / 特別カテゴリの個人データの露出、認証情報の侵害、機微データや管理機能への未認証アクセス、RCE、金銭の窃取。リリースを止める |
| **P1 / Major** | 現実的な条件（認証済みの攻撃者、前提条件 1 つ）で悪用可能な深刻な弱点、または機能していると信じられているが実際には機能しない制御 |
| **P2 / Minor** | 影響範囲が限定的、または前提条件が起こりにくい実在の欠陥。多層防御の欠落 |
| **Info** | 直接的なセキュリティ上の影響なし：ハードニング、衛生面、カバレッジに関する注記 |

スキャナの表現ではなく、結果と到達可能性で評価する。開発専用の依存関係に対するスキャナの "critical" は多くの場合
P2 であり、CVV を保持する目立たないスキーマのカラムは P0 である。

## 引き下げ不可の強制ルール

| 条件 | 下限 | 理由 |
|-----------|-------|-----|
| オーソリ後に SAD（CVV / トラック / PIN）を保存 | **P0**（暗号化していても） | PCI DSS v4.0.1 Req 3.3.1：暗号化しても「保存禁止」は免責されない |
| 平文の PAN を保存 | **P0** | PCI DSS v4.0.1 Req 3.5.1 |
| サーバー側またはサードパーティのリソースに認証できる有効な認証情報が、クライアント成果物（モバイルバンドル、`NEXT_PUBLIC_*`、`EXPO_PUBLIC_*`、JS バンドル）に含まれて配布されている | **P0** | 定義上公開されている。サーバー側の緩和策で引き下げることはできない。ハードコードされた*ローカル*暗号鍵は MASVS-CRYPTO-2 / CWE-321 であり、重大度は結果による（通常 P1） |
| 既知の悪意ある依存関係（OSV `MAL-*`）がインストールされている | **P0** | インストール時に実行されたものとみなし、到達し得たものをローテーションする |
| 機能しないセキュリティ制御（失敗し得ない verify/validate/authz） | **P1 以上** | 機能しているという思い込みこそが脆弱性である |
| authz/verify/決済の経路で例外時にフェイルオープン | **P1 以上** | OWASP Top 10:2025 A10 |
| 信頼できないコンテンツ（ドキュメント、Web ページ、issue / MR の本文、ツール出力）が、エージェントの事前承認された書き込み / 実行 / 公開アクションに到達する | **P1 以上**（デプロイ用シークレットや金銭が絡む場合は P0） | OWASP Top 10 for Agentic Applications 2026 ASI01 / ASI02 |
| 1 つのエージェントまたはツールセットが、非公開データ + 信頼できないコンテンツ + 持ち出し経路を同時に持つ（致命的な三要素（lethal trifecta）） | **P1 以上**（書き込みや金銭が絡む場合は P0） | 持ち出しに追加のバグは不要。LLM Top 10 2026 LLM01 / LLM02 |
| シークレットや個人データを含むプロンプト / トランスクリプトのログがコミットされている | **P1 以上** | コミットされたシークレットと同様に扱う：ローテーションし、その後に履歴を消去する |
| フェイルオープンするエージェントのガードレール、フック、deny ルール | **P1 以上** | 機能しない制御（上の行）に該当 |
| デプロイされたランタイム / サーバー / 製品のバージョンが、CISA KEV の CVE、または IPA / JPCERT/CC の注意喚起が直ちに修正を求める CVE の影響を受け、インターネットから到達できる | 認証前の RCE / 認証回避なら **P0**、それ以外は **P1 以上** | どこかで悪用が進行している。`reference/method/threat-intel.md` |
| 管理 / BI / 管理用コンソールやデータストアに外部から認証なしで到達できる、またはシークレットを含むファイルが配信される Web ルート配下にある | **P1 以上**（データやコード実行が絡む場合は P0） | 国の CERT が注意喚起する攻撃キャンペーンで大規模にスキャンされる初期侵入経路 |
| 測定も構造的な論拠もない性能上の主張 | **指摘事項としない** | 最大でも Info |
| より信頼度の低い主体が何も得ない、ベストプラクティスの欠如（境界の行がない。下記参照） | **Info**（`kind: configuration`、「ハードニング」） | ハードニングの注記は脆弱性ではない。確認済みの P0/P1 の影響を広げる場合にのみ P2 |

テスト / デモ用の値であることが明らかな git 履歴内のシークレット（サンプルアプリ、文書化されたフィクスチャ）も
報告する。重大度はその認証情報が到達し得る範囲で決め、その理由を記載する。

## 確度（重大度とは別の軸）

| 確度 | 意味 | 必要な根拠 |
|-----------|---------|-------------------|
| `confirmed` | コード経路を端から端まで読んだ：ソース -> シンクの間に有効な制御がない | ソース、シンク、欠落 / 破綻している制御の file:line |
| `likely` | パターンが存在し到達可能と考えられるが、1 つのつながりが未証明（例：ミドルウェアの順序、実行時の設定） | 未証明のつながりを明記する |
| `needs-runtime-check` | 静的監査では見えないデプロイ / 実行時の状態に依存する | 何を確認すべきかを正確に記載する |

`needs-runtime-check` の P0 は、報告書の表のタイトル行でその旨を明記せずに報告してはならない。
`needs-runtime-check` の指摘事項は、判定を妨げている要因（それを決めるデプロイ上の事実 1 つ。例：「metabase サービスの
3000 番ポートは本番の compose ファイルで公開されているか」）と、それを確認できる人を検証の欄に記載する - 担当者に
渡すのは推測ではなくチェックリストである。

**境界の行。** P0-P2 のすべての候補は `主体 -> 突破される制御 -> 影響を受けるリソース` を記載する
（「認証されていないインターネットのユーザー -> PUT /users/{id}/role の認可の欠落 -> 任意のアカウントのロール」）。
3 つすべてを埋められない候補は、ハードニングの注記（Info）であるか、指摘事項ではない。
誰も読んでいないスキャナの検出は指摘事項ではない。候補のままである。

## 敵対的検証（誤検知フィルタ）

P0/P1（および詳細モードではすべての P2）を登録する前に、それを**反証**することを試みる：
1. この時点で入力は本当に攻撃者が制御できるか。エントリポイントまで遡って追跡する。
2. 無害化する制御が別の場所にないか：ミドルウェア、フレームワークの既定動作（ORM のパラメータ化、テンプレートの
   自動エスケープ）、ゲートウェイ、スキーマ検証。推測せず、実際に読む。
3. そのコードは本番環境で到達可能か（デッドコードでない、テスト専用でない、無効化されたフラグの背後にない）。
4. 実際に関わるデータを踏まえて、主張する結果が本当に生じるか。
反証された場合 -> 理由を記録したうえで除外または格下げする。反証に耐えた場合 -> `confirmed` または `likely`。
標準/詳細モードでは、これを検証エージェントのサブエージェント（`agents/finding-verifier.md`）に委任する。

**ルールによる自動反証（レーンより前）。** `normalize_findings.py` がスキャナ候補に
`auto_refuted: <reason>` を付けるのは、ほぼ確実に実在しない場合のみである：HEAD でのシークレット検出のうち、一致した
値（プロセス内で読み、決して出力しない）がプレースホルダー（`dummy`、`example`、`sample`、`test`、
`fake`、`changeme`、`your_*_here`、`xxx`、`<...>`、`${...}`、`{{...}}`、`***`、同一文字の
繰り返し）であるもの、またはドキュメント/サンプルファイル内のより弱いプレースホルダー語。ベンダリングされた
サードパーティのドキュメント（`.agents/skills/`、`node_modules/`、`vendor/`、`third_party/`）内の短く低エントロピーの値。
テストファイルまたはベンダリングされたコード内の、本番専用の SAST ルール（CORS、CSRF、debug、cookie のフラグ、全インターフェースへのバインド、
healthcheck、USER の欠如、セキュリティヘッダー、TLS 検証、弱い乱数、一時ファイル）。レーンと
検証エージェントはこれらを飛ばし、報告書は Refuted の下に列挙する。**決して自動反証しないもの：** git 履歴にのみ
存在するシークレット、秘密鍵、一致した行のどこかに実際の鍵形式を持つ値
（`AKIA...`、`ghp_...`、`xox...`、`sk_live_` / `sk_test_` / `sk_prod_`、`AIza...`、`glpat-`）、クラウド、
カード、JWT のルール、長い高エントロピーの値、読めない行、およびその他すべてのルールとカテゴリ。

## 依存関係の優先順位付け
順序：OSV `MAL-*`（悪意あり）> CISA KEV 掲載（https://www.cisa.gov/known-exploited-vulnerabilities-catalog）
> 国の CERT の注意喚起（IPA、JPCERT/CC）で名指しされている > EPSS >= 0.1（FIRST EPSS）> CVSS v4.0 base >= 7
（v4 がなければ v3.1）> その他。ロックファイル外のランタイム、サーバー、製品は `intel.md` から得る
（`reference/method/threat-intel.md`）。格下げは到達可能性の論拠がある場合に限る：コールグラフの根拠（govulncheck、OSV-Scanner のコール解析）、または脆弱な関数 / インポートが
本番経路に決して乗らないこと（開発専用、テスト専用、任意のプラットフォーム依存、ビルドされないサンプルフォルダ）を
示す手動トレース。影響なしの判断は理由とともに記録する（任意で OpenVEX / CycloneDX VEX として
`<audit_dir>/work/<repo>/vex.json` に）。依存関係の指摘事項には、パッケージごとに修正済みの最小バージョンを必ず記載する。

## 根本原因による重複排除

1 つのコミットされた鍵を 2 つのスキャナが検出 = 指摘事項 1 件。1 つの authz チェック欠落に 3 つのルール ID =
指摘事項 1 件。1 つの古いパッケージに 20 件の CVE = 指摘事項 1 件（アップグレード）。10 個のルートから呼ばれる
1 つの脆弱なヘルパー = 呼び出し箇所を列挙した指摘事項 1 件。スキャナの検出は根本原因に付随する根拠であり、
個別の指摘事項ではない。重大度はトリアージ時に 1 回だけ付ける。ランタイムのアップグレードも 1 件の指摘事項である：
「PHP 8.3.30 -> 8.3.36 に上げて再ビルドする」は、すべての CVE と変更が必要なすべての指定箇所を列挙する。

**派生パターンの洗い出し。** P0/P1 を確認したら、同じ根本原因の字句的・構造的な派生（同じヘルパー、兄弟ルートでの
同じガードの欠落、別のサービスでの同じパターン）を grep し、レーンを閉じる前に該当箇所をその指摘事項に追加する。
**最も弱い経路：** 機微な効果（ロール変更、支払い、エクスポート、削除、MFA のリセット）ごとに、それを生むすべての経路
（UI のルート、API、モバイルのエンドポイント、バッチジョブ、インポート、リトライ、管理ツール）を列挙して制御を比較する。
最も弱い経路が指摘事項になる。

## 根拠付け

各指摘事項には次を持たせる：`file:line`（ソースとシンクが異なる場合は両方。保存データの場合はカラム +
マイグレーション。データそのものは決して記載しない）、`standard + version + requirement ID`
（`reference/standards/index.md`）、該当する場合は CWE、`confirmed_by`（スキャナ+ルール、`manual review`、
またはその両方。手動のみでも完全に有効）。
`scripts/validate_findings.py --repo name=path` で根拠が解決できるかを確認する。

## コミットされたシークレット：「露出」ではなく「侵害済み」

是正策は**プロバイダ側でのローテーション**であり、その後に必要なら履歴を整理する。ファイルを削除しても何も
直らない。シークレットの指摘事項には次を記載する：どのコンソールでローテーションするか、ローテーション時に何が
壊れるか（更新 / 再デプロイが必要な利用側）、履歴に残っているか（ノーマライザの `history-only` フラグ）、
クライアント成果物に含まれて配布されたか（P0 の強制ルール）。値は決して貼り付けない。gitleaks の出力は
マスク済みである。

## 職務分離とライフサイクル

監査者は監査対象のコードを決して変更もマージもしない（OWASP AISVS 1.01 Appendix C AC.4.1 / AC.8.1 / AC.8.4）。修正はユーザーが行う。
```
open -> (user fixes) -> re-scan with same pinned image digests + ruleset (+ re-read for manual findings)
     -> reproduces? yes -> stays open
                    no  -> catching rule still present? (rule out drift) -> closed
accepted-risk / false-positive: only with the user's recorded decision and reason
```
