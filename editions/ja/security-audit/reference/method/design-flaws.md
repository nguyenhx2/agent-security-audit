# スキャナに見えないもの：読解による設計レベルの欠陥の探索

スキャナはコード内に「存在する」パターンを見つける。最も危険な欠陥は、「存在しない」コード、機能している
*ように見えるだけ*の制御、あるいは 2 か所に分かれて食い違う状態に関するものである。パターンマッチでは
これらは見つからない。人間やエージェントが**読み、仮説を立てる**ことで見つける（`SKILL.md` の
Phase 1 と Phase 4）。本ファイルは、読解中に念頭に置くべき欠陥クラスのチェックリストである。

## スキャナがこれらを見逃す構造的な理由

スキャナは「この悪いパターンが存在する」とは主張できる。しかし「この必要な制御が存在しない」とは主張できない。
不在には照合すべきパターンがないからである。また意図を推論できないため、実行されるが何もしない制御は、
機能している制御と同じに見える。さらに一度に 1 ファイルしか見ないため、個々には問題ないが互いに矛盾する
2 つのコンポーネントは素通りする。

## 欠陥クラス

| クラス | どのように見えるか | 読解による探し方 |
|-------|--------------------|---------------------------|
| **クライアント側のみの認可** | 見つけるべきサーバー側のチェックがそもそも存在しない。UI はボタンを隠しているが、その背後の API エンドポイントには authz がない | 特権を要するエンドポイントをすべて列挙する。それぞれについてサーバー側の authz チェックを探す。欠落は SAST からは見えない。不在こそがバグである |
| **機能しないセキュリティ制御** | 常に true / null / 何もしない処理を返す `validateSignature()` / `verifyToken()` / `checkPermission()` が、あらゆる箇所で律儀に呼ばれている。制御は機能していると*信じられている* | 呼び出し箇所だけでなく、セキュリティ上重要なすべての関数の本体を読む。失敗し得ない制御こそが脆弱性である。P1 以上（`reference/method/triage.md`） |
| **食い違う 2 つのキャッシュ** | インメモリキャッシュと共有キャッシュ（例：Redis）、または権限キャッシュと DB が、同じ問いに異なる答えを保持し得る | すべてのキャッシュを見つける。何がそれを無効化するのか、1 つのキーに対して 2 つの層が異なる値を返し得るかを問う。古くなった authz キャッシュはアクセス制御の欠陥である |
| **保存データの機微情報** | カード / 個人情報 / PHI が暗号化されずに、または可逆な形で永続化されている。欠陥はロジックではなくスキーマにある | 手順の全体は `reference/method/sensitive-data-at-rest.md`。マイグレーションを最初に見る。これは Phase 2 であり、決済 / 個人情報 / PHI を扱うリポジトリでは必須 |
| **リポジトリをまたぐシークレットの供給元** | 環境変数から正しく読まれているシークレットが、実は別のリポジトリにコミットされた認証情報から設定されている | 環境変数の出どころを追跡する。`process.env.X` の読み取りが一見クリーンでも、インフラ / デプロイ用リポジトリでコミットされた値から `X` が設定されていればクリーンではない。スキャナは一度に 1 リポジトリしか見ない |
| **信頼境界での制御の欠落** | 信頼できないデータが入ってくる箇所に、レート制限、入力検証、出力エンコーディングがない | まず信頼境界を洗い出す（外部入力、サードパーティのコールバック、サービス間呼び出し）。各境界について、本来それを守るべき制御を確認する |
| **ロジック / 認可範囲の欠陥** | ユーザー A が ID を変更するだけでユーザー B のレコードを読める。ワークフローの手順を飛ばせる | オブジェクトの所有関係と状態遷移について推論する。IDOR や broken-object-level-authorization は設計上の欠陥であり、パターンの検出ではない（OWASP API Security Top 10） |
| **隠れていることは保護ではない** | UI が一度も呼ばないルート（ロール変更、ユーザー作成、なりすまし、一括エクスポート）が依然として応答する。呼ぶべきでないことを知っていたのはクライアントだけだからである | `routes.json` と、すべてのクライアントの API 呼び出し（Web のバンドル、モバイルアプリ、生成されたクライアント）を突き合わせる。どのクライアントも呼ばないルートには、それぞれサーバー側のロールチェックが必要である - それを読む |
| **スコープのない 1 つのクエリ** | テナントのスコープはグローバルスコープやミドルウェアで実現されているが、生の SQL、`unscoped()`、service-role のクライアント、バックグラウンドジョブ、エクスポートで迂回される | すべての DB クライアントと生のクエリを列挙し、それぞれのテナント条件を確認する。ユーザーやテナントを含まずに組み立てたキャッシュとストレージのキーも同様 |
| **信頼された ID ヘッダー** | バックエンドが認証プロキシの設定するヘッダー（`X-User`、`X-Forwarded-User`）からユーザー / テナントを受け取り、リクエストがプロキシを経由したことを確認しない | 認証ミドルウェアでのヘッダーの読み取りを探し、バックエンドのポートに直接到達できるか（compose / Kubernetes のポート）を確認する |
| **同じ効果に至る最も弱い経路** | ロール変更、支払い、エクスポート、削除、MFA のリセットに、異なる制御を持つ複数の経路（UI、API、モバイル、バッチ、インポート、管理ツール）から到達できる | 機微な効果ごとに、それを生むすべての経路を列挙して制御を比較する。最も弱い経路が指摘になる |
| **すべての複製に届かない失効** | 無効化されたユーザーや削除されたメンバーが、API トークン、キャッシュされた権限、JWT のクレーム、ソケット、キュー内のジョブを通じてアクセスを保持する | 無効化 / メンバー削除のハンドラが何を無効にするかを読み、無効にしないものを列挙する |

## 探し方（手法）

1. **まず信頼境界を洗い出す。** 信頼できないデータはどこから入るか。外部リクエスト、Webhook や決済の
   コールバック、メッセージキュー、サービス間呼び出し、ファイル / CSV のインポート。ガードを探す前に
   境界を描く。
2. **特権を要する各アクションについて、サーバー側の制御を見つける**。名前だけでなく本体を読む。`true` を返す
   `checkAccess` という名前の制御は、偽りの安心感をもたらすため、制御がないよりも悪い。
3. **ファイルではなくデータを追う。** 決済プロバイダのレスポンス、ユーザー ID、キャッシュされた権限を
   ファイルをまたいで追跡する。単一ファイルのスキャナにはできないが、あなたにはできる。
4. すべてのキャッシュと、保存されたすべての派生値について **「何がこれを無効化するのか」を問う**。2 つの
   信頼できる情報源の食い違いは、スキャナが決して見ない欠陥クラスである。
5. **シークレットについてはリポジトリの境界を越える。** クリーンな環境変数の読み取りでも、別の場所にコミット
   された認証情報が供給元になり得る。監査の対象は 1 つのリポジトリではなく*システム*である。

## トリアージへの引き渡し

設計レベルの指摘事項には**スキャナの裏付けがない**ことが多い。その `confirmed_by` は "manual review" であり、
それで完全に有効である（`reference/method/triage.md`）。スキャナの指摘事項とまったく同じように、`file:line` と
要件（`reference/standards/index.md`）に根拠付けする。機能しないセキュリティ制御とクライアント側のみの authz の欠落には
重大度の下限がある。スキャナの検出がないことを理由に過小評価してはならない。
