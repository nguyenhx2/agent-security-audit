# 保存データの機微情報：誰もが見落とす観点

これがこのスキルの存在理由である。実際のプロジェクトで、開発者が顧客の決済カードデータを暗号化せずに
そのままデータベースへ保存していた。標準的な SAST はそれを検出しなかった。コントローラやサービスを読んだ
レビュー担当者も全員が素通りした。**欠陥がビジネスロジックではなくスキーマにある**からである。決済、個人情報、
健康データに関わるすべての監査で、これを最優先かつ必須のフェーズとする。

手順に戻る：`SKILL.md` の Phase 2。本ファイルを参照する重大度の強制ルール：
`reference/method/triage.md`。

## PCI DSS の 2 つのクラス（是正策は正反対であり、チームはよく混同する）

PCI DSS の現行バージョン：**v4.0.1**（v4.0 の限定改訂。v3.2.1 は廃止済み）。要件は番号だけでなく
`PCI DSS v4.0.1 Req X.Y.Z` の形で引用する。バージョン付き ID については `reference/standards/index.md` を参照。

| クラス | データ | ルール | 是正策 | 落とし穴 |
|-------|------|------|--------|----------|
| **NEVER-STORE（保存禁止）**（SAD = 機密認証データ） | 磁気ストライプ / トラックデータ全体（track1、track2）、カード検証値（CVV / CVC / CVC2 / CID）、PIN / PIN ブロック | **Req 3.3.1**：オーソリ後は保存してはならない（MUST NOT）。**暗号化していても同様**。v4.0.1 では、正当かつ文書化された業務上の必要性があるカード*発行者*に限り、狭い例外がある | カラムを**削除**し、ログ、キャッシュ、バックアップから消去する。暗号化しても免責されない | 「CVV は暗号化した」は**緩和策ではなく指摘事項**である。暗号化が勤勉さに*感じられる*からこそ、チームが最も誤るルールである |
| **MUST-BE-UNREADABLE（判読不能化必須）** | PAN（カード会員番号） | **Req 3.5.1**：**保存されるあらゆる場所で**判読不能にする：強力な暗号、トランケーション、トークン化、または（弱い手段として）ハッシュ化。保存には文書化された業務上の正当性が必要 | トークン化 / 暗号化 / トランケーション。正当性がある場合のみ保持する | **ハッシュ化した PAN は「良い」のではなく「弱い」**。評価してはならない。下記を参照 |

### ハッシュ化した PAN が「良い」のではなく「弱い」理由
キー空間が総当たりできるほど小さい。BIN（先頭 6-8 桁）が既知の 16 桁の PAN に Luhn チェックの制約を加えると、
候補は 10^12 を大きく下回り、オフラインで容易に列挙できる。指摘事項にはその旨を明記する。ハッシュ化した PAN は、
実際には PAN を判読不能にしていない MUST-BE-UNREADABLE の制御であり、合格ではなく弱い / 不十分な制御として扱う。

### 同じ確認で併せてスイープする隣接クラス
- **可逆に**保存されたパスワード：アルゴリズムを問わず、復元可能 = 誤り（暗号化は可逆であり、それが目的であり
  問題でもある）。パスワードはソルト付きの一方向ハッシュでなければならない。
- 参照（トークン、外部キー）で足りる場面で、個人情報全体を永続化している。
- 上記のいずれかが**ログ**に現れる。
- **LLM / エージェントの領域：** 会話およびメッセージのテーブル、保存された生成結果、ベクトルストア
  （個人データの埋め込みは個人データである）、評価用データセット、ファインチューニング用 JSONL、フィードバックの
  テーブル、トレースのエクスポート（LangSmith / Langfuse）、およびコミットされたプロンプト / トランスクリプトのログ
  （`prompt_history*`、`.specstory/`、`.claude/projects/*.jsonl`、Aider の履歴）。作業ツリーと git 履歴の両方が
  対象（`agent-config.md` が両方を列挙する）。閲覧は、シークレット、メールアドレス、電話番号、個人データのキーを
  マスクする `peek.py` でのみ行う。
- **コミットされたデータファイル**（`.sqlite`、`.db`、`.xlsx`、`.csv`、ダンプ、`.har`、`.eml`）：スイープは
  これらをファイル名で列挙する（`data_files_committed`）。名前とサイズから判断し、開く場合は peek.py 経由のみとする。

## まずスイープを実行する（数秒、場所のみ）

正確なコマンドは SKILL.md の Phase 2 を参照（`--out <audit_dir>/work/<repo>/sweep.json`。プロジェクト固有の
カラム名には `--extra-terms local_col_a,local_col_b` を追加する）。マイグレーション -> スキーマ -> 永続化呼び出し -> ログ -> クライアント側ストア -> キャッシュ -> エクスポートの順に
走査し、検出を分類する（SAD の保存禁止、PAN、可逆な認証情報、保存されたシークレット、国民 ID、連絡先の個人情報、
健康、生体、日本語 / ベトナム語のネイティブ表記の用語）。数字の並びはマスクされ、Luhn 検査を通るリテラルは場所のみが
報告される。何を検索したかを常に記録するため、クリーンな結果も根拠になる。
**検出は手がかりである**。以下の手順で、読解によりそれを確認する。

## 検出手順：順序が重要（低コストで信号の強いものから）

1. **マイグレーション：すべて。** カラム名が根拠であり、これは最も低コストなスイープである。古い
   マイグレーションも省略しない。後で削除されたカラムからも、かつて設計上何を保存していたかがわかり、データが
   バックアップに残っている可能性がある。
2. **エンティティ / モデル / スキーマの定義**（JSON / JSONB カラムを含む）。JSON の塊には、カラム名からは
   わからないカードのオブジェクトが隠れていることがあるため、宣言された型だけでなく、そこに*書き込まれる*内容を
   確認する。`metadata jsonb` からは何もわからない。オブジェクトを組み立てるコードがそれを教えてくれる。
3. **決済プロバイダのレスポンスから何が永続化されるか。** `save(response)` は、誰もそのために設計していない
   テーブルにカードデータが入り込む典型的な経路である。ゲートウェイのレスポンス本文には、アプリが必要とする以上の
   ものが日常的に含まれる。プロバイダのクライアントの戻り値を、すべての `.save()` / `INSERT` / `create()` まで追跡する。
4. **漏出先**：機微データが主たるストアの外へ漏れ出す場所。
   ログ、キャッシュ（インメモリおよび共有、例：Redis）、分析 / イベントのパイプライン、CSV / Excel の
   エクスポート経路、マテリアライズドビュー、データベースのバックアップ、サードパーティ API への送信ペイロード。
5. **クライアント側のストア**：モバイルの設定ファイル / キーストア、ブラウザの `localStorage` /
   `sessionStorage` / IndexedDB。

## Grep の語彙（大文字小文字を区別しない。現地語の変種を追加する）

```
cvv  cvc  cvc2  cid  card_number  cardnumber  card_no  pan  credit_card  creditcard
track  track1  track2  pin_block  expiry  exp_month  exp_year  card_holder  cardholder
security_code
```

これらをまずマイグレーションとスキーマに対して実行し、次にモデル / シリアライザ / ログ出力のコードに対して実行する。
プロジェクトの現地語による同等の語（例：翻訳されたカラム名）を追加する。検出は手がかりであり判定ではない。
カラムが実際に何を保存しているかを読んで確認する。

## 報告のルール（譲れない）

- **カード番号は決して出力しない**：実在のものも、テスト値も、トランケートしたものも同様。**カラム名**と
  **`file:line`** を報告する。根拠はデータではなく、場所とカラムである。
- **「該当なし」も結果である。** 「<date> に <files/globs> を <patterns> で検索し、何も見つからなかった」
  を監査の指摘事項として記録する。黙って何も書かないことは結果ではない。後の読み手は「確認してクリーン」と
  「確認していない」を区別できない。
- すべての監査報告書には、何か見つかったかどうかにかかわらず、**保存データの機微情報**のセクションを設ける。
  `templates/audit-report.md.template` を参照。

## 重大度（全体のモデルは `reference/method/triage.md` を参照）

- オーソリ後に SAD（CVV/トラック/PIN）を保存 -> **P0（暗号化していても）**。
- 平文の PAN を保存 -> **P0**。
- ハッシュ化した PAN -> 弱い制御。重大度は露出と正当性で決め、合格とは決してしない。
- 可逆に保存されたパスワード -> P1（ストアに攻撃者が到達できる場合、または鍵がその横にある場合は P0）。

## 中立的な例（構造のみ。実データなし）

決済テーブルが `card_number varchar` と `cvv varchar` を宣言しており、どちらも
`{{path/to/payment.service}}:{{line}}` でゲートウェイのレスポンスから直接書き込まれている。指摘事項は 2 件で、
クラスは別々である：
- `cvv` カラム -> NEVER-STORE 違反（PCI DSS v4.0.1 Req 3.3.1）、P0。是正策：カラムを削除し、
  ログ / キャッシュ / バックアップから消去する。「暗号化する」は受け入れない。
- `card_number` カラム -> MUST-BE-UNREADABLE（PCI DSS v4.0.1 Req 3.5.1）、平文なら P0。是正策：
  トークン化または削除。保持する場合はその正当性を示す。
